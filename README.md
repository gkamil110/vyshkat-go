
# ВышКат

Домашнее задание №1 по КПО. Консольное приложение на Go для учёта транспорта и вещей в парке кикшеринга.

## Как запустить

Нужен Go 1.22 или новее. Откройте терминал в папке проекта и выполните:

```bash
go run ./cmd/vyshkat
```

Сначала программа показывает демо, затем открывается меню. Демо использует отдельный парк, поэтому после него пользователь начинает с пустого списка.

Другие варианты запуска:

```bash
go run ./cmd/vyshkat -no-demo    # сразу открыть меню
go run ./cmd/vyshkat -demo-only  # показать только демо
```

## Возможности программы

- Добавление самокатов, велосипедов и электровелосипедов. Перед добавлением транспорт проходит техосмотр.
- Учёт шлемов, док-станций и зарядных шкафов.
- Подсчёт количества транспорта и вещей, а также общего расхода энергии за сутки.
- Список транспорта для новичков: простота использования от 6 до 10.
- Просмотр всего имущества с названиями и инвентарными номерами.
- Проверка неправильного ввода и повторяющихся инвентарных номеров.

Данные хранятся в памяти. После закрытия программы они не сохраняются.

### Как проходит техосмотр

`ServiceCenter` проверяет тормоза и рулевое управление. У электротранспорта дополнительно проверяется электрическая часть. Если что-то неисправно, транспорт в парк не добавляется.

Это упрощённая модель техосмотра: состояние устройства вводится через консоль. Оценка простоты использования не влияет на решение о технической исправности.

## Структура проекта

| Папка | За что отвечает |
|---|---|
| `cmd/vyshkat` | Запуск приложения |
| `internal/domain` | Транспорт, вещи и интерфейсы |
| `internal/application` | Приёмка, учёт и отчёты |
| `internal/inspection` | Проверка исправности транспорта |
| `internal/storage` | Хранение объектов в памяти |
| `internal/di` | Контейнер зависимостей |
| `internal/bootstrap` | Создание и настройка зависимостей |
| `internal/console` | Меню и работа с вводом пользователя |
| `internal/demo` | Примеры работы программы |

`FleetService` не работает напрямую с конкретным репозиторием или центром техосмотра. Он получает интерфейсы `Repository` и `Inspector`. В `bootstrap.NewContainer()` указываются их реализации, а `bootstrap.Fleet()` создаёт готовый сервис.

## SOLID

- **S — Single Responsibility.** `ServiceCenter` проверяет технику, `MemoryRepository` хранит данные, `Console` отвечает за ввод и вывод, а `FleetService` выполняет основные операции с парком.
- **O — Open/Closed.** `FleetService` использует интерфейс `Transport`, поэтому новый тип транспорта можно добавить без изменения основной логики приёмки и отчётов.
- **L — Liskov Substitution.** Вместо одного вида транспорта можно передать другой, если он реализует `Transport` и выполняет его контракт.
- **I — Interface Segregation.** Для инвентаризации и потребления энергии существуют отдельные интерфейсы `InventoryItem` и `EnergyConsumer`. Например, обычному велосипеду не нужен метод расхода электричества.
- **D — Dependency Inversion.** `FleetService` зависит от интерфейсов `Inspector` и `Repository`, а не от `ServiceCenter` и `MemoryRepository` напрямую.

Общие поля вынесены в `baseItem` и `transportBase`. В Go здесь используется встраивание структур и интерфейсы, а не наследование классов.

### Где пришлось ограничить SOLID

Принцип Open/Closed не полностью соблюдается в консольном меню: если добавить новый вид транспорта, нужно будет добавить для него пункт и вызов конструктора в `console.addTransport()`. Для трёх видов транспорта это проще, чем вводить отдельную систему фабрик для меню. При этом `FleetService` менять не потребуется, если новый транспорт подходит под существующие правила.

## DI и подмена техосмотра

В `internal/di` реализован небольшой контейнер. Он умеет регистрировать зависимости, создавать их при первом обращении, сохранять созданные экземпляры и обнаруживать циклические зависимости.

В тесте `TestCanReplaceInspectionThroughDI` настоящий `ServiceCenter` заменяется на `fakeCenter` с помощью `container.Replace()`. Так проверяется, что решение о приёмке действительно приходит от переданного инспектора. После создания сервисов подмена запрещена.

## Как можно расширить программу

- **Новый транспорт:** добавить тип, реализующий `Transport`, и возможность создать его через меню. Для электрического транспорта также нужен `EnergyConsumer`. Если правила техосмотра будут отличаться, потребуется изменить инспектора.
- **Сотрудники:** хранить отдельно от имущества. Сотрудник не должен реализовывать `InventoryItem`, поскольку люди не ставятся на баланс.
- **Склад запчастей:** можно вынести в отдельный сервис и репозиторий, не перегружая `FleetService`.

## Тесты

Запустить все проверки:

```bash
go test ./...
go test ./... -cover
go vet ./...
```

Основные проверки:

- `TestServiceCenter` — исправный и неисправный транспорт.
- `TestAdmissionRequiresInspection` — транспорт нельзя добавить без техосмотра.
- `TestSummaryAndBeginnerThreshold` — подсчёт имущества, энергии и отбор новичков.
- `TestCanReplaceInspectionThroughDI` — замена техосмотра через контейнер.
- `TestMemoryRepository` — проверка одинаковых номеров и копирования списка.
- `TestDemoShowsAllCoreScenarios` — демонстрационные сценарии.

На последней локальной проверке `go test ./...` прошёл во всех пакетах, `go vet ./...` не нашёл замечаний. Покрытие пакетов с тестами — от **77,4% до 100%**. Для `cmd/vyshkat` отдельные тесты не написаны, поэтому его покрытие равно 0%.

## Ограничения

Программа не сохраняет данные между запусками, не поддерживает одновременную работу нескольких пользователей и не заменяет настоящий технический осмотр. Эти возможности можно добавить позднее, не меняя основную предметную модель.
